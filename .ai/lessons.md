# Development Lessons

Record only durable, project-specific lessons that should change future implementation or review decisions.

Use one concise entry per lesson:

`Context -> Problem -> Rule -> Applies to`

## Lessons

Supabase project changes -> CLI use was explicitly rejected for connected work -> Use the Supabase MCP for inspection, migrations, generated types, advisors, and database verification; keep exact migrations source controlled -> All agent-driven Supabase work
Overlapping ERP skills -> Repeated rules can create ambiguous ownership even when they agree -> Declare what each skill owns and cross-link complementary implementation guidance -> Local ERP platform skills
Scoped server-confirmed mutations -> A full shop-data refresh made simple status buttons wait on unrelated slow queries -> Return the authoritative changed value and patch only the affected entity in context -> Single-record CRUD and milestone actions
Timezone correction migrations -> Future trigger logic was fixed while legacy UTC-derived completion dates remained wrong -> Include a narrowly scoped, audited backfill and verify boundary records whenever persisted business-date semantics change -> ERP dates derived from timestamps
Production-route data isolation -> Clearing the shared shop cache on entry left every app view empty when returning from a station -> Preserve same-user, same-tenant data across route changes and revalidate it on exit; clear only when the authenticated data scope changes -> Full-screen production routes backed by narrow snapshots
Production-event time series -> Automatic week/month bucketing relabeled scrap events onto a shared period-start date -> When a report promises the recorded date, filter by the selected period but aggregate on each event's plant-local `created_at` calendar day -> Scrap and other immutable production-event charts
Order Q&A content -> UI-only sanitization can be bypassed and silent URL removal obscures why a message changed -> Normalize markup/control characters to plain text, reject links and executable URI schemes explicitly, render only text nodes, and mirror the restriction with a database check -> Manufacturer and customer chat messages
Conversation retention lifecycle -> A scheduled archive flag would duplicate sales-order completion state and require background infrastructure -> Derive active/archived status from authoritative completion facts and the plant-local closing date, preserve archived history, and block replies through the shared mutation boundary -> Sales-order-linked Q&A
Additive columns on restricted tables -> A new customer field was omitted from explicit column-level grants and returned 403 despite correct RLS -> Every client-writable column migration must extend and test the applicable column grants -> Supabase tables with narrowed INSERT or UPDATE privileges
Shop-floor QR authentication -> A second device/PIN identity layer made phones re-enroll after browser state changed -> Use normal Supabase plant-staff sessions for authentication and treat traveler QR codes as same-origin navigation only -> Phone production access and QR scanning
Client auth transitions -> A valid session briefly coexisted with an unresolved profile and routed an existing user into onboarding -> Treat session and profile resolution as one blocking auth state and never render login, account creation, or onboarding decisions until it settles -> Supabase auth bootstrap, sign-in, and auth route guards
Browser capability deployment headers -> The QR scanner UI was correct but production denied both camera access and its blob-worker decoder -> Audit Permissions-Policy and CSP alongside implementation, then exercise the fallback path under production headers -> Camera, worker, clipboard, and other policy-gated browser features
Parallel ERP libraries -> A card grid diverged from the established Sales Order and Work Order execution pattern -> Use the existing full-width search/filter toolbar and roomy row-list structure unless a different presentation is explicitly requested -> Tool, order, and other operational library screens
Tool-master operational notes -> Notes visible only in the library were missing where the tool was selected and used -> Resolve current master notes onto loaded assignments and render them in selectors, operation views, and regenerated travelers while labeling assignment notes separately -> Cutting-tool routing and Work Order consumers
Tool Assembly terminology -> Generic description/notes fields obscured the intended short identity and longer explanation -> Model and display Tool Assemblies as name/description, keeping any legacy persistence naming isolated at the service boundary -> Tool Library and tooling-assignment consumers
Tool Assembly identity -> Editable assembly numbers could collide or drift from order-style document identity -> Generate immutable tenant-scoped Tool Assembly IDs atomically in PostgreSQL and default a blank name to that ID -> Tool Assembly create/edit flows and persistence
Physical Tool Assembly identity -> Quantity grouping hides dimension differences between nominally similar assemblies -> Represent every complete Tool Assembly as one uniquely identified physical asset and model checkout as a one-asset state transition -> Tool master, checkout, assignment availability, and migrations
Append-only asset state -> Transaction timestamps can tie within one database transaction and UUID order does not represent event order -> Give state-transition events a database-generated sequence and derive current state from that sequence -> Tool checkout and other append-only current-state projections
Tool checkout production gate -> An operation assignment did not prove the physical Tool Assembly had left the crib, and active tooling could be returned early -> Require every operation-assigned assembly to be checked out before production events and block check-in while derived active usage exists -> Work Order production and Tool Library checkout
Tool checkout transfer semantics -> Quantity entering a routing step does not mean its operation has started using assigned tooling -> Warn when destination tooling is unchecked, but enforce checkout only when production is recorded at that operation -> Production transfers, operator notices, and Work Order warnings
QR action navigation -> Auth redirection preserved only the pathname and silently dropped action query parameters -> Preserve pathname, search, and hash through sign-in so scanned action URLs complete their intended workflow -> Tool labels and other authenticated QR destinations
Shared shop QR scanner -> A production-only route parser rejected valid Tool Assembly labels and encouraged duplicate scanning flows -> Keep one strict same-origin scanner with an explicit allowlist for traveler and Tool Assembly destinations -> Mobile ShopCore QR navigation
